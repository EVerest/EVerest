# EVerest 2026.10.0-rc2

This is the second release candidate for **EVerest 2026.10.0**. These notes cover the changes since [2026.10.0-rc1](https://github.com/EVerest/EVerest/releases/tag/2026.10.0-rc1); see there for everything since 2026.02.1. Please test it on your hardware and report regressions before the final release.

## Changes that may need action

- **EVerest API modules reject invalid requests** instead of executing them. ([details](https://everest.github.io/release_2026_10_0_rc2/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-apis), #3289)
  - The request must be a JSON object, and `headers` must be an object.
  - `replyTo` must be a string and a valid topic outside the topics EVerest itself uses.
  - Clients that receive replies on `everest_api/.../e2m/<operation>` must add a level of their own, for example `e2m/<operation>/<uuid>`.
  - Numbers that do not fit their type are rejected; they used to wrap around.
- **Commands without arguments carry `{}`.** In `evse_board_support_API` and `system_API`, `cp_state_X1`, `cp_state_F`, `cp_state_E`, `lock`, `unlock`, `self_test` and `allow_firmware_installation` carry an empty JSON object as payload. Clients that test for an empty payload must accept `{}`. (#3289)
- **Date-times in the EVerest APIs** must be RFC 3339 with a UTC offset, between `1677-09-21T00:12:43.146Z` and `2262-04-11T23:46:49.854Z`. Other values, such as a missing offset or `9999-12-31T23:59:59Z`, discard the message with a warning. For an open end, use `2262-04-11T23:46:49.854Z`. (#3298)
- **`power_supply_DC_API` clients must deliver less than their minimum.** When the EV asks for less than the offered minimum, EvseManager sends that current, down to 0 A, instead of raising it to `min_export_current_A` or `min_import_current_A` (IEC 61851-23:2023 CC.5.5.7). The client must then deliver no current. In-tree power supply drivers switch their output off. (#3065)
- **edm 0.9.0 or newer.** An older edm in `PATH` fails configure. edm reads only the top-level `dependencies.yaml`, and builds a dependency from a local source tree only if its `source_dir` names it; `EVEREST_EDM_WORKSPACE` is dropped. (#3151)
- **ChargeBridge firmware 0.8.4.** `pionix_chargebridge` uses configuration version 7. (#3326)
- **Out-of-tree modules on internal interfaces:** the `evse_manager` `reserve` command takes a `ReserveRequest` instead of a bare reservation id (#3257), and the `ISO15118_charger` variable `ac_contactor_closed` is renamed to `contactor_closed` (#3169).

## Behavior changes

- EvseManager requests state X1 only with `cp_state_X1`; a 100 % duty cycle was sent as `pwm_on(100)`. (#3293)
- `powermeter/VendorWarning` and `ac_rcd/VendorWarning` no longer make the EVSE Inoperative. (#3370)
- EvseSlac reports MATCHING on the first CM_SLAC_PARM.REQ instead of when armed on CP state B. (#3133)
- A gap in voltage measurements no longer fails the cable check by itself (`cable_check_measurement_timeout_s`). (#2682)
- DC stop follows IEC 61851-23 Table CC.9: PowerDeliveryRes waits for the contactors to open, EVSE_Shutdown is also sent for EV-initiated stops, and the power meter transaction ends after welding detection. WeldingDetectionRes reports the voltage behind the contactors, selected with EvseManager `welding_detection_voltage_source` (default `powermeter_car_side`). (#3169)
- A V2G session ended by a timeout switches to X1 together with the TCP FIN instead of 0.5 s later. EvseManager runs the ISO 15118-3 error sequence when an established data link is lost, also without 5 % PWM. (#3384)
- ISO 15118-20 sessions without TLS offer EIM only. Plug & Charge accepts only contract certificates. (#3342, #3343)
- ISO 15118-20 rejects a PowerDeliveryReq whose EVPowerProfile exceeds the offered schedule (FAILED_EVPowerProfileInvalid), and ScheduleExchangeRes offers the EVSE maximum charge power. (#3060)
- In ISO 15118-2, the selected value-added services are reported only after a successful authorization, so the Internet VAS opens its uplink only for authorized EVs. (#3340)
- `EvseV2G` always ends the session after a FAILED PaymentDetailsRes or AuthorizationRes, regardless of `terminate_connection_on_failed_response`. (#3338)
- `Iso15118InternetVas` forwards only the offered TCP ports and DNS to the announced resolvers, to public addresses through the WAN interface, and restores the previous forwarding setting on teardown. (#3339)
- OCPP: incoming messages are limited to `MaxIncomingMessageSize` (default 4 MiB, connection closed with 1009), messages nested deeper than 64 levels are rejected, and out-of-range numbers get a FormationViolation. (#3330, #3348, #3254)
- OCPP 1.6 no longer shifts `atTime` of triggered meter values by `TimeOffset`. (#3299)
- OCPP 2.1 composite schedules sum per-phase W values. (#3229)
- RFC 3339 timestamps are parsed strictly and `±HH:MM` offsets are applied. Date-times outside 1677–2262 are rejected instead of wrapping around. OCPP 1.6 accepts the usual ISO 8601 deviations. (#3240, #3298)

## New features

- `evse_manager_consumer_API` `session_info` carries the details of the reservation that holds the EVSE. (#3257)
- Errors carry an optional `trigger_value`, exposed in the error JSON, everestpy and the external APIs, and available as `${trigger_value}` in the OCPP custom error mapping. (#3117)
- `everest::io` and `everest::tls` clients bind a chosen source port range and write TLS key logs. (#3286)

## EV simulation

- The new `Ev15118` module is the EV side of the C++ ISO 15118 stack (ISO 15118-20, ISO 15118-2, DIN SPEC 70121). It replaces `PyEvJosev`, which is removed together with the Josev dependency, so EVerest no longer needs Java. To migrate, change `module: PyEvJosev` to `module: Ev15118` and set `supported_protocols`. ([details](https://everest.github.io/release_2026_10_0_rc2/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-iso15118-ev), #3031, #3034)
- Yocto images that installed `python3-iso15118` or the recipes only it pulled in, such as `openjdk`, must drop them; the recipes are removed. (#3034)

## Dependencies

OpenSSL 3.5.9 for Bazel builds, tokio 1.53.3, anyhow 1.0.103 (#3337); curl 8.23.0, date 3.0.5, ftxui 7.0.3, pugixml 1.16, pybind11 3.1.0, json-schema-validator 2.4.1 (#3302).
