**EVerest 2026.10.0** is the second stable release under the [six-month release strategy](https://everest.github.io/release_2026_10_0/project/releases/releases-and-versioning.html). It gets patch releases (2026.10.x) for bug and security fixes without breaking changes.

The notes cover the changes since **2026.02.2**. Changes already shipped in a 2026.02.x release are not repeated. If you upgrade from 2026.02.x, start with [Upgrade notes](#upgrade-notes): some of the changes need action before or during the upgrade. The full migration steps are in the documentation under [Upgrading to 2026.10](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html).

From this release on, public API components can be marked **experimental**. Experimental components have no stability guarantee and no deprecation period. They are listed in the [Experimental Feature Index](https://everest.github.io/release_2026_10_0/project/releases/experimental-index.html) and log a warning at startup. Everything else in the public API follows the [deprecation policy](https://everest.github.io/release_2026_10_0/project/releases/deprecation-policy.html).

## Highlights

- **Ready for AFIR.** This release covers the charger-side obligations of the EU Alternative Fuels Infrastructure Regulation (AFIR), including ISO 15118-20 ahead of the 1 January 2027 deadline. Compliance of a charger depends on the complete product.
- **DIN SPEC 70121 and ISO 15118-2 in the C++ stack.** `Evse15118D20` now serves DIN 70121, ISO 15118-2 (EIM, Plug & Charge) and ISO 15118-20 from one module, with each protocol selectable. It also supports ISO 15118-20 Plug & Charge with separate SECC leaf certificates for -2 and -20. The `EvseV2G` and `IsoMux` modules are deprecated in its favor, and a [migration guide](https://everest.github.io/release_2026_10_0/how-to-guides/iso15118-stack-migration.html) covers the switch.
- **Bidirectional and grid-supporting AC charging.** The C++ ISO 15118-20 stack implements AC DER for IEC (Annex L) and SAE (Annex M). OCPP 2.1 gains DER control (R04), central V2X control (Q03) and dynamic charging profiles (K28). OCPPmulti passes CSMS DER directives to the EV through the new `grid_support` interface.
- **One OCPP module for 1.6, 2.0.1 and 2.1.** The new `OCPPmulti` module implements all three protocol versions on one configuration and data storage based on the OCPP 2.x device model. Its `Mode` parameter selects one version or a preferred version with a fallback. The `OCPP` and `OCPP201` modules are deprecated in its favor, and a [migration guide](https://everest.github.io/release_2026_10_0/how-to-guides/ocpp-storage-migration.html) covers the switch.
- **Event-driven SLAC and ISO 15118-3 conformance.** The SLAC stack is rewritten around events, and EvseManager follows the ISO 15118-3 error sequences: X1 and E/F handling after a lost data link or D-LINK_ERROR, wake-up supervision, and a cap on SLAC retries. The DC stop sequence follows IEC 61851-23 Table CC.9. The ISO 15118 stacks received more than 20 conformance fixes from conformance-test runs.
- **Megawatt Charging System (MCS).** The new `McsDataLink` module supervises the ISO 15118-10 MCS data link over single-pair Ethernet. MCS is also supported on ChargeBridge, and the cable check uses the MCS isolation threshold.
- **Remote management of EVerest (experimental).** Two new management APIs in the manager let you manage a running charger over MQTT. The `configuration_API` creates, activates and deletes configuration slots, loads a complete configuration from YAML and changes module parameters at runtime. The `lifecycle_API` starts and stops the modules and reports their status. Used together, they switch a charger to a new configuration without restarting EVerest. Both are opt-in with `manager --configuration-api` and `--lifecycle-api`, and the `everest-management-api-cli` client covers every request. See [Management APIs](https://everest.github.io/release_2026_10_0/explanation/adapt-everest/management_apis.html).
- **New EVSE features.** Captive cable mode, AC current derating from temperature sensors (`AcTemperatureDerating`), AC charging with SoC through a DC HLC session, and wiring phase-rotation correction.
- **Security hardening.** Modules run with least privilege through Linux file capabilities, the EVerest APIs and the OCPP stack validate what they receive, and the handling of keys, credentials, certificates and downloads was hardened throughout.

## Upgrade notes

### Breaking changes

Changes to the public API that need action when upgrading. Each item states what to do.

- **Manager settings are no longer stored in the configuration database.** Schema migration 4 drops the `SETTING` table, so `manager --db <file>` on its own runs on built-in defaults. Keep non-default settings in a file passed with `--settings <file>`. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-manager-settings), #2412, #3197)
- **Linux capabilities come from file capabilities.** The manager no longer grants capabilities, and the `capabilities` key of a module entry is ignored, without a deprecation period. If `EvseSlac`, `PacketSniffer`, `Setup` or `Huawei_V100R023C10` runs unprivileged, grant file capabilities to their binaries. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-capabilities), #2976)
- **EVerest API modules reject invalid requests** instead of executing them. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-apis), #3289)
  - The request must be a JSON object, and `headers` must be an object.
  - `replyTo` must be a string and a valid topic outside the topics EVerest itself uses.
  - Clients that receive replies on `everest_api/.../e2m/<operation>` must add a level of their own, for example `e2m/<operation>/<uuid>`.
  - Numbers that do not fit their type are rejected; they used to wrap around.
- **Commands without arguments carry `{}`.** In `evse_board_support_API` and `system_API`, `cp_state_X1`, `cp_state_F`, `cp_state_E`, `lock`, `unlock`, `self_test` and `allow_firmware_installation` carry an empty JSON object as payload. Clients that test for an empty payload must accept `{}`. (#3289)
- **Date-times in the EVerest APIs** must be RFC 3339 with a UTC offset, between `1677-09-21T00:12:43.146Z` and `2262-04-11T23:46:49.854Z`. Other values, such as a missing offset or `9999-12-31T23:59:59Z`, discard the message with a warning. For an open end, use `2262-04-11T23:46:49.854Z`. (#3298)
- **Command and reply timeouts are shorter.** (#3428)
  - A command between modules fails with a command timeout after 120 s instead of 300 s.
  - In the EVerest API modules, `cfg_request_reply_to_s` has a default and maximum of 100 s instead of 550 s. A YAML configuration that sets a higher value is rejected. In a configuration database (`--db`), a stored higher value is replaced by the default with a warning (#3473).
  - API clients must reply within that time; afterwards the request is answered with the default response.
- **`power_supply_DC_API` clients must accept setpoints below their minimum, down to 0 A.** When the EV asks for less than the offered minimum, EvseManager sends that current, down to 0 A, instead of raising it to `min_export_current_A` or `min_import_current_A` (IEC 61851-23:2023 CC.5.5.7). The client must then deliver no current. In-tree power supply drivers switch their output off. (#3065)
- **`RsIskraMeter` `read_meter_values_interval_ms`** is limited to 1000–4000 ms (default 2000). Larger values fail validation. (#3165)

### Other changes that need action

These changes are outside the public API but affect start scripts, service units and builds.

- **Manager command line.** Spell options in full, and `manager --check` requires `--config`. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-manager-cli), #2528, #2412)
- **edm 0.9.0 or newer.** An older edm in `PATH` fails configure. edm reads only the top-level `dependencies.yaml`, and builds a dependency from a local source tree only if its `source_dir` names it; `EVEREST_EDM_WORKSPACE` is dropped. (#3151)
- **Yocto.** Shared recipes moved to the `meta-everest-common` layer and use `${UNPACKDIR}`, and the compatibility recipes for the former `lib*` repositories are removed. A wrynose layer is added. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#yocto), #3149, #3110)
- **Yocto `everest.service`.** The manager runs with `--db /var/lib/everest/everest.db` and `--settings /etc/everest/settings-mqtt-uds.yaml`. The database is initialized from `config.yaml` on the first start, so later edits of `config.yaml` have no effect, and a `settings:` block in it is ignored. Keep `/var/lib/everest` across root file system updates. The recommended `everest-mosquitto-config` package runs the internal MQTT traffic over the Unix socket `/run/mosquitto/mosquitto.sock`; local TCP clients reach every topic except `everest/`. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#yocto), #3220)
- **Yocto images without Josev.** The `python3-iso15118` recipe and the recipes only it pulled in, such as `openjdk`, are removed. Images that installed them must drop them. (#3034)
- **ChargeBridge firmware 0.8.4.** `pionix_chargebridge` uses configuration version 7. (#3326)

### Behavior changes

These changes need no action in most setups, but they change what a running system does.

**EVSE**

- With `ac_limit_slac_init_retries: true` (default), EvseManager limits SLAC retries per ISO 15118-3: at most two E/F retries per plug-in at 5 % PWM, then basic charging. Set it to `false` for unlimited retries. (#3062)
- Errors from the SLAC and ISO 15118 modules now feed EvseManager's fault handling. Anything other than `generic/VendorWarning` from them makes the EVSE Inoperative. (#2368)
- `ac_rcd/VendorWarning` raised through the board support module no longer makes the EVSE Inoperative. (#3370)
- EvseManager requests state X1 only with `cp_state_X1`; a 100 % duty cycle was sent as `pwm_on(100)`. (#3293)
- EvseSlac reports MATCHING on the first CM_SLAC_PARM.REQ instead of when armed on CP state B. (#3133)
- With EIM before matching, the B-C-B toggles of CM_VALIDATE at nominal PWM are no longer taken as charge requests. A state C during the matching closes the contactor once it has lasted 1 s or when the matching ends. A data link lost while basic AC charging at nominal PWM is paused runs the X1, E/F sequence. (#3420)
- On a V2G_SECC_CommunicationSetup_Timeout the V2G connection is closed right away and D-LINK_ERROR follows 300 ms later, so the FIN reaches the EV before EvseSlac leaves the logical network. EvseManager runs the ISO 15118-3 error sequence when an established data link is lost, also without 5 % PWM, and skips the legacy wakeup through state E/F while a data link is established. (#3384, #3417)
- DC stop follows IEC 61851-23 Table CC.9: PowerDeliveryRes waits for the contactors to open and carries EVSE_Shutdown also for EV-initiated stops, and the power meter transaction ends after welding detection. WeldingDetectionRes reports EVSE_Ready unless the charger itself stops the session or a fault is active. It reports the voltage behind the contactors, selected with EvseManager `ev_side_voltage_source` (default `powermeter_car_side`; the key was named `welding_detection_voltage_source` in rc2 and rc3). (#3169, #3407, #3471)
- A gap in voltage measurements no longer fails the cable check by itself (`cable_check_measurement_timeout_s`). (#2682)
- `Evse15118D20` `negative_bidirectional_limits` defaults to `true`, so ISO 15118-20 discharge limits are sent as negative values. Set it to `false` to keep positive limits. (#3013)
- ISO 15118-20 sessions without TLS offer EIM only. Plug & Charge accepts only contract certificates. (#3342, #3343)
- ISO 15118-20 rejects a PowerDeliveryReq whose EVPowerProfile exceeds the offered schedule (FAILED_EVPowerProfileInvalid), and ScheduleExchangeRes offers the EVSE maximum charge power. (#3060)
- In ISO 15118-2, the selected value-added services are reported only after a successful authorization, so the Internet VAS opens its uplink only for authorized EVs. (#3340)
- `EvseV2G` always ends the session after a FAILED PaymentDetailsRes or AuthorizationRes, regardless of `terminate_connection_on_failed_response`. (#3338)
- EvseV2G retries network startup every second instead of exiting when its interface isn't ready, and raises `generic/CommunicationFault` meanwhile. (#2369)
- `Iso15118InternetVas` forwards only the offered TCP ports and DNS to the announced resolvers, to public addresses through the WAN interface, and restores the previous forwarding setting on teardown. (#3339)
- `install_ca_certificate` rejects certificates that are not CA certificates (InvalidCertificateChain) and sub-CA certificates whose issuer is not installed (NoRootCertificateInstalled). OCPP answers both with Rejected. Such certificates used to be accepted but could neither be listed nor deleted. (#3355)
- `GenericPowermeter` raises `powermeter/CommunicationFault` after two failed read cycles and stops republishing stale values. With EvseManager `fail_on_powermeter_errors` (default `true`), an unreachable meter makes the EVSE Inoperative after about 5 s. (#2673)
- `CarloGavazzi_EM580` reports the device serial number as `meter_id`, not the module id. (#1972)
- `InfyPower_BEG1K075G` reports negative current while importing. (#1986)

**OCPP**

- OCPP 2.x component config: connection profiles move to per-slot `NetworkConfiguration_<N>` components and are migrated at startup, and stored `minLimit`/`maxLimit` are kept. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#ocpp-2-x-component-configuration), #1934, #2231)
- Components missing from the device model config directory are kept, with a warning.
- The device model holds its values in memory. Edit the device model database only while EVerest is stopped, and `"persistent": false` in a custom component config takes effect. (#3154)
- CSMS messages nested deeper than 64 levels are rejected. (#3348)
- OCPP 2.x accepts RequestStartTransaction without `evseId` when an EVSE is free; it used to be rejected. (#2308)
- OCPP 2.x MeterValues carry a configured Frequency measurand, and `Energy.Active.Import.Register` is no longer reported twice for readings with signed per-phase values but no signed total. (#3415)
- OCPP 2.1 composite schedules sum per-phase W values. (#3229)
- OCPP 1.6 sends the signed `Transaction.Begin` meter value in its own MeterValues.req right after StartTransaction. (#2252)
- OCPP 1.6 no longer shifts `atTime` of triggered meter values by `TimeOffset`. (#3299)
- Prices and session costs are rounded to the nearest minor currency unit instead of truncated; EUR 0.29 used to become 28 cents. (#3382)
- The message of an EVerest error reaches the CSMS: as `info` or `vendorId` in OCPP 1.6, and as `techInfo` in OCPP 2.x. (#2456)
- Diagnostics files are named `diagnostics-YYYY-MM-DDTHH-MM-SSZ` (UTC, no colons). (#2908)
- `System` stores the boot reason `ScheduledReset` for a scheduled reset (OCPP `OnIdle`) instead of `RemoteReset`. (#3414)

**Platform**

- File-based SQLite databases (configuration, OCPP, device model) use WAL mode.
- The configuration database records whether a parameter value came from a manifest default or was set explicitly. When a slot is loaded, stored defaults follow the defaults of the current manifests; explicitly set values are never changed. In a database written by an earlier version, a value that the new manifest rejects is replaced by the manifest default with a warning, also if it had been set explicitly. ([details](https://everest.github.io/release_2026_10_0/explanation/configuration-service.html), #3473)
- Date-times outside 1677–2262 are rejected instead of wrapping around. OCPP 1.6 accepts the usual ISO 8601 deviations. (#3298)
- EVerest API modules publish compact JSON; the content is unchanged. (#2637)
- `evse_manager_consumer_API` publishes the session event `SessionResumed` as specified. Earlier releases sent `SessionResumed:` with a trailing colon, so clients that match that value must change. (#3490)
- `PacketSniffer` names capture files after the capture device. (#2873)

## Removed

- The admin panel backend and controller built into the manager, the CMake options `EVEREST_ENABLE_ADMIN_PANEL_BACKEND` and `EVEREST_INSTALL_ADMIN_PANEL`, and the Yocto admin-panel packages. The standalone everest-admin-panel replaces them. (#3057)
- The built-in session logger of `Evse15118D20`. (#2453)
- The `PyEvJosev` simulation module and the Josev dependency, so EVerest no longer needs Java. The new `Ev15118` module is the EV side of the C++ ISO 15118 stack and replaces it: change `module: PyEvJosev` to `module: Ev15118` and set `supported_protocols`. ([details](https://everest.github.io/release_2026_10_0/project/releases/upgrading-to-2026.10.html#project-upgrading-to-2026-10-iso15118-ev), #3031, #3034)

## New features

### New modules

- `OCPPmulti`: OCPP 1.6, 2.0.1 and 2.1 in one module. (#2332, #2829)
- `AcTemperatureDerating`: AC current limits interpolated from temperature-sensor readings. (#2325)
- `McsDataLink`: supervises the ISO 15118-10 MCS data link. (#2696)
- `charger_information_API`: lets an external client supply vendor, model, serial numbers and firmware version. (#2871)

### EVSE (EvseManager, Auth, energy management, EvseSecurity)

- Captive cable mode: `keep_cable_locked` keeps the cable locked whenever a plug is present; only `force_unlock` releases it. (#2884)
- AC charging with SoC through a DC HLC session, with configurable EV reinitialization. (#2221)
- `phase_rotation` and `phase_rotation_grid_side` correct a rotated L1/L2/L3 wiring of power meter readings. (#2430)
- Auth: `stop_transaction_on_reswipe` (#2530), the `PlugEventsLIFO` selection algorithm (#2344), and BankCard tokens can stop transactions (#2613).
- EnergyNode publishes its rated limits as capabilities, also on `external_energy_limits_consumer_API`. (#1916)
- EvseSecurity certificate store limits are configurable. (#2980)
- ISO 15118-20 AC DER: EvseManager selects the DER flavour (`iso15118_der_flavor`) and advertises `ac_nominal_frequency` and `ac_max_reactive_power`. (#2608, #2446)
- Power meters can return a signed start value, which is forwarded with the OCPP transaction start. (#2214)
- EvseManager `session_logging_console` (default `true`): set it to `false` to keep the session log files and MQTT output without printing every entry to the EVerest log. (#3491)

### OCPP

- OCPP 2.1: DER control R04 (#2100), central V2X control Q03 (#2067), dynamic charging profiles K28 (#2279), `maxOfflineDuration` and `invalidAfterOfflineDuration` (#2968, #1852).
- OCPPmulti integrates DER with per-EVSE `grid_support` providers and NotifyDERAlarm. (#2472)
- OCPP 1.6 on the device model: multi-slot network configuration with failover (#2550), and EVerest-supplied components readable and writable in 1.6 mode (#2596).
- Custom OCPP 1.6 key mappings in OCPPmulti (experimental): a file given with `Ocpp16KeyMappingsPath` maps custom OCPP 1.6 keys to device model variables. An entry for a built-in key stored in `OCPP16LegacyCtrlr`, such as `LightIntensity`, replaces the built-in mapping, so OCPP 1.6 and OCPP 2.x share the station's own variable. ([details](https://everest.github.io/release_2026_10_0/how-to-guides/ocpp-storage-migration.html#howto-ocpp-storage-migration-custom-key-mappings), #3225, #3226)
- New OCPP 1.6 keys: `ReportSuspendedEVSEReasonChange` (#2571), `ReportClearedErrors` (#2455), `RejectRemoteStartTransactionWithoutConnectorId` and `RemoteStartTransactionWithoutConnectorIdFindFirst` (#2461), `SwitchSecurityProfileConnectionTimeout` (#2276).
- New OCPP 2.x variables: `OCPPCommCtrlr.QueueNotifyEventMessages` (#2568) and `InternalCtrlr.DeferFirmwareDownloadDuringTransaction` (#2480).
- Firmware updates can keep connectors available during install (#2327, #2336, #2337). `System` can skip the reset after an update (`ResetAfterUpdate`, #2400).
- Custom error mapping in OCPPmulti (experimental): a mapping file changes how individual EVerest errors are reported in OCPP 1.6 StatusNotification and OCPP 2.x NotifyEvent, on top of one built-in mapping shared by both versions. A faulty entry is logged and ignored. (#2999)
- OCPP201 accepts a custom MREC mapping. (#2193)
- Composite schedules carry the stack level of the winning profile in OCPP 2.x. (#2242)
- OCPP201 implements the `stop`, `restart`, `change_availability` and `monitor_variables` commands. (#2124)
- OCPP 1.6 configuration changes can be vetoed by a validation callback, and readOnly custom keys can be written locally (libocpp). (#2590)

### ISO 15118 and SLAC (charger side)

- `Evse15118D20` runs DIN 70121, ISO 15118-2 and ISO 15118-20, selectable per protocol. (#2485)
- ISO 15118-20 Plug & Charge and separate SECC leaf certificates for -2 and -20 (OCPP 2.1 V2G20Certificate). (#3013)
- ISO 15118-20 AC DER IEC (Annex L) and SAE (Annex M), with the `grid_support` interface. (#2354, #2355, #2370, #2423, #2445, #2607, #2608)
- The TLS server serves several certificate chains on one port and rotates certificates without a restart. (#2226)
- EvseV2G and Evse15118D20 ports are configurable, so two instances can run behind IsoMux. (#2434)
- Supported app protocols can be narrowed at runtime. (#1866)
- `selecting_sap_based_on_energy_service` for EVs predating AMD1 semantics. (#2301)
- `Evse15118D20` `ac_close_contactor_timeout_ms` (100 to 10000 ms, default 1400): how long the SECC waits in ISO 15118-20 AC for the contactor to close before it answers FAILED_ContactorError. The default is the previous fixed value and the highest conformant one. (#3380)
- ISO 15118 session, TLS and certificate telemetry. (#2311)

### EVerest APIs

- Consumer APIs answer `<topic>/get` with the last published value, so late-joining clients don't wait for the next update. (#2457)
- `ocpp_consumer_API`: `connection_status` (#2552), `implementation_ready` (#2574), `monitor_and_get_variables` (#2585), `change_availability` and `security_event` (#2534), OCPP message callbacks (#1978), and transaction event timestamps (#2720, #2721).
- `evse_manager_consumer_API`: `reserved` flag and the details of the reservation that holds the EVSE in `session_info` (#3018, #3257); `charge_mode` and `hlc_capable` per connector, plus `evse_id_din` in `get_evse` (#2705, #2702).
- Errors carry an optional `trigger_value`, exposed in the error JSON, everestpy and the EVerest APIs, and available as `${trigger_value}` in the OCPP custom error mapping. (#3117)
- `system_API` relays `configure_network` (#2413) and firmware update metadata (#2336).
- RpcApi 1.1.0 (AC DER enums). (#2833)
- 17 EVerest API specifications are at version 1.1.0; the others, including the new ones, stay at 1.0.0. (#3213)

### Manager, framework and build

- `--settings <file>` takes the manager settings from a dedicated file, validated against `schemas/settings.yaml`. Example files are installed to `etc/everest/settings-*.yaml`. (#3197, #3206)
- `--user-config <path>` places the user-config outside the config directory, for example when that is read-only. (#3199)
- `--mqtt_everest_prefix` lets several EVerest instances share one broker. (#2036)
- The manager notifies modules of configuration changes on `config/updates`. (#3116)
- MQTT-C is replaced by mosquitto, and modules can publish retained external MQTT messages. (#1799, #2180)

- `everest::io` and `everest::tls` clients bind a chosen source port range and write TLS key logs. (#3286)

## Notable fixes

This list covers crashes, security-relevant fixes and conformance fixes. The release contains more than 200 further fixes; see the full changelog.

### EVSE

- Reservations survive a reboot and carry their real id. Consumed reservations are cancelled. (#2929, #2927)
- IEC 61851-1: X1 is held for at least 3 s before PWM is re-enabled. (#3015)
- ISO 15118-3 error sequences after a lost data link and after wake-up. (#3061, #3136, #3140)
- MCS cable check uses the 125 kΩ isolation threshold. (#2452)
- EvseManager no longer crashes during shutdown. (#2649)
- AC Plug & Charge without a charging loop: EvseManager keeps the HLC session until the data link ends, then continues with basic charging. (#3132)
- The EV maximum limits are kept when a CurrentDemandReq omits them. (#3294)
- `ErrorHistory` resets its database only when the schema is incompatible; a database that lacked columns used to be kept while every insert failed. (#3432)

### Framework

- Invalid MQTT messages no longer terminate modules: malformed payloads, unknown message types, excessive JSON nesting, invalid UTF-8 and command results that arrive after the timeout are logged and ignored. (#3026)
- A module with several configuration service requests in flight receives the reply to each request; one caller could get another's reply while the other timed out. (#3406)

### OCPP

- Crash fixes: Reset deadlock in OCPPmulti (#3020), unknown EVSE in change_availability (#2591), DataTransfer payloads (#2588), over-long error strings (#2509), and a device model data race (#2587).
- OCPP 2.x keeps running when handling a CSMS message throws, and answers the CALL with InternalError. (#3349)
- OCPP 2.x reconnects honor `RetryBackOff` and the configured attempt count, fall back to the last working profile, and don't lose the call in flight during a profile switch. (#2475, #3021)
- The websocket no longer hangs on shutdown when a wakeup of its callback thread was lost. Messages still queued when the connection is cleared fail at once instead of after the message timeout. (#3394)
- Monitoring: Delta monitors measure from their last trigger, monitor ids are validated, and SetVariableMonitoring cannot change hardwired monitors. (#3123, #3452)
- Status and availability: StatusNotification Unavailable after ChangeAvailability(Inoperative) (#2477), effective connector status (#2481), and reservations cleared on authorization (#2928).
- Component names are matched case-insensitively (#2977). Valueless variables return Accepted (#3137).
- OCPP 1.6 Daily and Weekly recurring charging profiles no longer start one second early for every leap second since `startSchedule`. (#3354)
- Firmware and log upload state machines conform to the OCTT test cases. (#2931, #2930, #2892, #2943, #2973)
- `ISO15118Ctrlr.Enabled` reflects whether HLC is enabled. (#2708)

### ISO 15118 and SLAC

- Memory safety: EXI bitstream bounds and V2GTP parsing (#2813), and the ScheduleExchange stack overflow (#2850).
- EvseSlac binds CM_VALIDATE and its match window to the EV's own session. (#3334)
- `EvseV2G` ignores SIGPIPE; an EV that reset the TLS connection during shutdown could end the module process. (#3390)
- Only a paused session with the EV still plugged in can be resumed. (#3345)
- `Evse15118D20` survives a missing or removed network device. (#3290)
- A SessionStop before charging, for example from an EV that gives up during authorization, is reported as an HLC failure with the reason of that phase. (#3070)
- EXI codec: X509SerialNumber values above 127 are encoded correctly. (#3181)
- Conformance fixes in the ISO 15118 stacks. (#1983, #2312, #2603, #2953, #3017, #3085, #3093, #3094, #3095, #3097, #3098, #3099, #3103, #3261)

### Hardware drivers

- `Huawei_V100R023C10` loads OpenSSL providers explicitly, so a TPM-held client key works when the module runs with file capabilities. (#3456)
- `CarloGavazzi_EM580` recovers the transaction left on the device when EVerest restarts during a session, bounded by `startup_transaction_state_timeout_s` (default 30 s). (#3251)
- `CarloGavazzi_EM580` reads live measurements at a fixed rate and warns only when reads are skipped, at most once per minute; the warning used to appear with every device state read. (#3487)
- `InfyPower_BEG1K075G` reconnects when the CAN device disappears and raises `power_supply_DC/CommunicationFault` meanwhile. (#3258)

## Security

2026.10.0 contains all security fixes of the 2026.02.x patch releases up to 2026.02.2. The advisories are listed under [Security Advisories](https://github.com/EVerest/EVerest/security/advisories); each names the versions that contain its fix.

Further hardening in this release: the EVerest APIs validate requests against their specifications (#3289); the OCPP stack rejects deeply nested messages (#3348); secrets are removed from logs (#3166); curl arguments are separated from URLs (#3068).
